# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Terraform provider for [OWASP DefectDojo](https://github.com/DefectDojo/django-DefectDojo), built with the [Terraform Plugin Framework](https://github.com/hashicorp/terraform-plugin-framework). Provider code lives in `internal/provider/`. The API client is a separate module, [go-defectdojo](https://github.com/ottramst/go-defectdojo) (same author, MIT): a resource that needs an endpoint the client lacks starts with a pull request there. DefectDojo API behavior is documented in go-defectdojo's `CLAUDE.md` ("DefectDojo API quirks"); keep new findings there.

The provider supports and tests the latest patch of the two newest DefectDojo minor releases (currently 3.4.304 and 3.5.103), listed once in `.github/defectdojo-versions.json`. DefectDojo 2.x is not supported: 3.0 removed the role-based access endpoints (groups, members, roles) from the open-source edition, and access is granted with `authorized_users` on product types and products. Most configuration endpoints need a superuser.

Scope is DefectDojo's configuration, planned as milestones: product types, products and engagements (v0.1.0); SLA configurations, users, notifications and webhooks (v0.2.0); system settings and Jira (v0.3.0); lookup objects (v0.4.0); list resources and migration from `doximity/defectdojo` (v0.5.0); compatibility guarantees (v1.0.0). Runtime data (findings, tests, imports) is out of scope. Endpoints removed in DefectDojo 3.6 (tool types, tool configurations, API scan configurations) are not supported.

## Common Commands

```bash
make default          # fmt, lint, install, generate (full dev cycle)
make build            # Build binary
make lint             # Run golangci-lint
make fmt              # Format Go code with gofmt
make generate         # Generate provider documentation (tfplugindocs) + terraform fmt examples
make test             # Unit tests (120s timeout, parallel=10)
make up               # Start DefectDojo (DD_VERSION defaults to the newest supported)
make testacc          # Acceptance tests against it
make down             # Stop it and delete its data
```

Run a single test:
```bash
make testacc TESTARGS='-run TestAccProductType'
```

## Running Acceptance Tests Locally

```bash
make up                        # DefectDojo 3.5.103 on http://localhost:8080, about 30 seconds
# make down && make up DD_VERSION=3.4.304
make testacc
make down
```

The compose stack (shared with go-defectdojo) is PostgreSQL (tmpfs), Valkey, a one-shot `initializer`, `uwsgi`, and DefectDojo's `nginx` on `127.0.0.1:8080`; Celery is left out, and deletes are synchronous. The `GNUmakefile` exports `DEFECTDOJO_URL`, `DEFECTDOJO_USERNAME` (`admin`) and `DEFECTDOJO_PASSWORD` (`DefectDojoAcc1!`) for the tests unless they are set. `testAccPreCheck` fails the test, never skips it, when they are missing. The initializer loads fixtures: the product type "Research and Development" (id 1), the SLA configurations "Default" (id 1, which can't be deleted) and "No SLA Enforced" (id 2), development environments, regulations and test types.

## Architecture

**Provider entry point:** `main.go` → `internal/provider/provider.go`

`Configure()` builds a `*defectdojo.Client` from `url` and `api_token`, or `username` and `password` (basic auth, which also works when API tokens are disabled; the token wins when both are set), each falling back to a `DEFECTDOJO_*` environment variable. There is no version probe: DefectDojo's only version source is its 860 KB OpenAPI schema, which `defectdojo_jira_project` reads only for its 3.5.103-only setting. The client is passed to every resource and data source (`configureResource`, `configureDataSource` in `helpers.go`).

**Resource pattern** (all files in `internal/provider/`; `resource_product_type.go` is the template):
- Files are `resource_<name>.go` and `data_source_<name>.go`; constructors are `New<Name>Resource` and `New<Name>DataSource`, registered in `Resources()` and `DataSources()`.
- Each resource has a struct holding the `*defectdojo.Client` and a model struct with `tfsdk` tags. IDs are DefectDojo's integer IDs, as `types.Int64`.
- `Read()` removes the resource from state on `defectdojo.ErrNotFound` with `removeGone`, which sets the identity first (the framework rejects a null identity after `Read` even when the state is removed, and a state taken over from `doximity/defectdojo` or used with Terraform before 1.12 has none); deletes of already-deleted objects succeed.
- Errors use descriptive titles: `"Error creating DefectDojo product type"`, with the object ID in the detail.
- Optional text attributes that DefectDojo stores as `""` or null map to null (`stringOrNull`) and reject `""`, so there is no perpetual diff.
- DefectDojo strips leading and trailing whitespace from text fields (Python `str.strip`, Unicode-aware), which would make apply fail with "inconsistent result" (a heredoc ends in `\n`): text attributes use `noSurroundingWhitespace()`. Lengths are characters, not bytes: use `stringvalidator.UTF8LengthBetween`.
- `Update()` uses the client's `Patch` methods with `Nullable` fields, so attributes the configuration doesn't manage are kept. Optional+Computed attributes that others may manage (such as `authorized_users`) use `UseStateForUnknown` and are only sent when the **configuration** sets them: the plan holds the prior state value when they are not configured, so read `req.Config`, not the plan. The `*_requests_test.go` tests check the request bodies against `fakeDefectDojo`, a fake DefectDojo serving one object of a collection (also in its list, filtered by the query) and read-only objects of other collections (`lists`), recording POST and PATCH bodies (`checkPostSends`, `checkPatchSends`, `checkPatchExactly`); with `singleton` (and `id`) it serves a pre-seeded object that, like the system settings, has no POST, DELETE or GET by ID (405), and `writeCount` counts the writes; `setList` replaces another collection's objects during a test. A change made elsewhere between plan and apply then fails the apply ("inconsistent result") instead of being overwritten; that is intended, and documented on the attribute.
- **Tags** (`tags` on products and engagements): a set of strings with `tagValidators()` (1–255 characters, no spaces, commas or quotes, no two differing only in case) and `tagSet(tags, reference)`, which deduplicates DefectDojo's tags ignoring case and keeps the spelling of the reference (the plan in `Create`/`Update`, the prior state in `Read`): DefectDojo gives a tag the spelling of an existing tag that matches it ignoring case.
- **Engagements** (`resource_engagement.go`): `read()` always hides the tags of the engagement's product (DefectDojo adds them when the product, or the system setting, passes them on, and doesn't say which are inherited) unless they are in a reference set: the plan in `Create`/`Update`, the prior state in `Read`, nothing after an import. `Create` reads the engagement back, because the create response may lack the inherited tags. After `Create` and `Update`, the state takes the planned tags when they are known (`keepPlannedTags`): DefectDojo's tags can lag behind (a product's tag change reaches engagements through Celery; inherited tags a write removes come back), and the next refresh reconciles them. `Update` sends `tags` when configured, and on a product move: the planned tags, or, when there are none, the new product's tags if it has `enable_product_tag_inheritance` (else `[]`, which leaves an engagement under the system-wide setting without tags until tags are written again), since any tag write makes DefectDojo swap the old product's inherited tags for the new one's. `status` and `engagement_type` are sent only when the plan differs from the state, so an unrelated change never reopens an engagement closed elsewhere. Dates are strings validated as `YYYY-MM-DD` (`dateValidator`), and `targetDatesValidator` checks start ≤ end, which DefectDojo checks only on create.
- **Users** (`resource_user.go`): `password_wo` is write-only (read from `req.Config`) and sent only by `Create`, since DefectDojo's API can't change a password. `configuration_permissions` are codenames: `Create`/`Update` map them to IDs with `ConfigurationPermissions.GetByCodename` (an unknown codename is an attribute error), and `Read` maps the IDs back with one `ListAll`, skipped when the user has none; that endpoint needs a superuser, so on a 403 the planned or prior value is kept, with a warning. The names can't be null in DefectDojo, so `Update` sends `""` to clear them.
- **Notification webhooks** (`resource_notification_webhook.go`): `header_value_wo` is write-only, with `header_value_wo_version` (each requires the other, and the value also `header_name`, without which DefectDojo never sends it). `Create` sends the value; `Update` sends it only when the version differs from the state's, which includes setting it after an import (a PATCH, unlike the replace of the Vaultwarden provider), and sends null when both are removed. DefectDojo returns the value in plain text; it is never stored. The status fields have no `UseStateForUnknown`, since DefectDojo's workers change them.
- **Notifications** (`resource_notifications.go`; the 17 events and `scan_added_empty` are written out one by one, from the same list as the client): the scope (`user_id`, `product_id`, `template`) forces replacement; `templateScopeValidator` rejects a user or product only for `template = true`. `Create` adopts the row of the scope (`Notifications.GetByScope`) with a PATCH of every event, or POSTs a new one; `Update` PATCHes every event (a PUT would reset the scope and can't update the template). `Delete` resets the system-wide and personal rows to DefectDojo's model defaults with a PATCH, and deletes product rows and the template. Every event is Optional+Computed with DefectDojo's default, so an unset event is reset.
- **Jira instances** (`resource_jira_instance.go`): `password_wo` is Optional and write-only, with an optional `password_wo_version`; `Create` sends it, and `Update` sends it, when set, when the version changes (also when it is removed) or when the URL changes (`jiraURLChanged` ignores a trailing slash, as DefectDojo does), since DefectDojo requires the password with a URL change. `ModifyPlan` requires it (null fails, unknown passes; Terraform plans again during the apply with the values known) on create, on a URL change (or an unknown URL) and on a new non-null version, so that an imported or generated instance plans without it. `Delete` counts the instance's Jira projects first (`CountJiraProjects`) and refuses, because DefectDojo answers the delete of an instance in use with a 500.
- **Jira projects** (`resource_jira_project.go`): `product_id` or `engagement_id` (`ExactlyOneOf`, `RequiresReplace`). `custom_fields`, `close_transition_fields` and `reopen_transition_fields` are `jsontypes.Normalized` with `jsonObjectValidator` (DefectDojo would take any JSON); a reformatted config value still plans an update, since semantic equality only applies to refreshes and applies. `project_key` and `component` aren't nullable in DefectDojo, so `Update` sends `""` to clear them. `Create` first lists the product's or engagement's Jira projects and refuses when one exists (DefectDojo would keep a second one for a product, unused). `slaNotificationValidator` rejects both SLA notification settings. `ModifyPlan` reads the server's version (`ServerVersion`, `compareVersions` in `helpers.go`) only when `suppress_sla_notification_comments` is planned true, and refuses it before 3.5.103; `Read` stores false when DefectDojo lacks it.
- **Lookup objects** (v0.4.0): `defectdojo_regulation`, `defectdojo_note_type`, `defectdojo_development_environment`, `defectdojo_cicd_infrastructure` (each with a data source), `defectdojo_announcement`, the product attribute resources and the `defectdojo_test_types` data source.
  - **Note types**: DefectDojo deletes a note type's notes with it, so `force_destroy` (default `false`) counts them first with the client's `NoteTypes.CountNotes` (the `Notes` entries of `delete_preview`). The tests keep their note types inactive, except in one step: an active mandatory type keeps the UI from closing findings.
  - **Development environments**: imports find a scan's environment by name, so `Create` and a rename refuse a name another environment has (`checkNameFree`), and a 409 on delete (tests use it) gets an explanation.
  - **Announcement**: DefectDojo keeps one, always with ID 1. `message` and `style` force replacement, so every user sees a new announcement (a PATCH doesn't re-show it to users who dismissed it); `dismissable` changes in place. `Create` refuses when one exists and suggests the import. Its acceptance test is a single function that fails if the stack has an announcement and leaves none.
  - **CI/CD infrastructure**: `infrastructure_type` forces replacement (DefectDojo ignores a change); a taken name of the same type (400 on create, 409 on rename) gets an explanation. The engagement's `cicd_*_id` attributes follow `lead_id` (null clears).
  - **Product attributes** (`resource_product_attribute.go`): one implementation for `defectdojo_product_platform`, `_lifecycle` and `_origin`, chosen by a `productAttributeKind`. `value` forces replacement; DefectDojo refuses to delete an entry products use (409), so the docs recommend `create_before_destroy`.
- **System settings** (`resource_system_settings.go`, `data_source_system_settings.go`, `system_settings_fields.go`): about 70 settings, so the schema is generated from one table, `systemSettingsFields` (name, kind, description, validators), and the state is read and written attribute by attribute (`GetAttribute`/`SetAttribute`), not through a model struct. Values move through the client's JSON names: `systemSettingsValues` marshals the client's `SystemSettings` to a map, and `systemSettingsPatch` unmarshals a map of the configured settings into a `SystemSettingsPatch`; `TestSystemSettingsFields` checks that every name is a field of both and that every writable field is in the table (`read_only_mode` is left out on purpose). Every setting is Optional+Computed without a default, with `UseStateForUnknown`: `Create` and `Update` PATCH every setting the **configuration** sets, so an unset one keeps DefectDojo's value. Text settings keep `""` in the state (null configuration means unmanaged), unlike `stringOrNull`. `slack_token`, `msteams_url` and `jira_webhook_secret` are write-only with a `_wo_version`, sent when the planned version is set and differs from the state's; removing them sends nothing (`""` with a new version clears the Slack token and the Teams URL; DefectDojo rejects `""` for the Jira secret, and the provider never sends null). `ModifyPlan` checks the planned password lengths (minimum ≤ maximum, which DefectDojo doesn't), reading DefectDojo's value, on create, for the one the configuration leaves out. `Read` removes the resource when DefectDojo's ID differs from the state's (an import of the wrong ID); `Delete` sends nothing. A new DefectDojo setting is a row in the table (and a field in the client); gate it by version if older servers lack it.
- **Optional+Computed or plain Optional:** an attribute is Optional+Computed (with `UseStateForUnknown`, sent only when the configuration sets it) when other systems write it (`tags`, `authorized_users`, `regulation_ids`, `configuration_permissions`) or DefectDojo always fills it (`sla_configuration_id`, the engagement's `status` and `engagement_type`, the system settings); null then means "unmanaged". Every other attribute is plain Optional, and null clears it in DefectDojo; the descriptions of the references and numbers say so (`product_manager_id`, `lead_id`, `user_records`, `revenue`, the CI/CD links). The system settings keep `""` in the state, since null means unmanaged there and `""` is the only way to clear a text setting. `authorized_users` keeps DefectDojo's name, the one reference attribute without the `_id`/`_ids` suffix.
- Integers that DefectDojo stores in 32-bit columns have `int32Range()` (or a narrower range); IDs have `AtLeast(1)`. Validators only reject what DefectDojo rejects, or what it would store differently and so fail the apply with an inconsistent result (`noSurroundingWhitespace()`, `""` for optional text): from v1.0.0, a validator that rejects a value that applies today is a breaking change.
- Reference attributes (user IDs, lookups) map DefectDojo's null to null (`int64OrNull`, `stringOrNull`); `Update` sends them with `nullableInt`/`nullableString`, so null clears them. Attribute names must avoid Terraform's reserved root names (`lifecycle`, `count`, `provider`, ...): the product lifecycle is `life_cycle`, as in `doximity/defectdojo`.
- **Cascading deletes:** deleting a product type, product or engagement deletes everything below it, down to findings. Such resources have `force_destroy` (default `false`): `Delete()` counts the children first and refuses with an error naming them. After the DELETE, `waitForDeletion` polls until the object is gone, for servers with `DD_ASYNC_OBJECT_DELETE`.
- **Resource identity:** every resource implements `resource.ResourceWithIdentity` with the identity `id` (`idIdentitySchema`, `setIDIdentity`), set in `Create`, `Read` and `Update`. `ImportState` uses `importByID`, which accepts a numeric import ID or the identity. Changing an identity schema needs an identity upgrader and an upgrade test.
- **List resources** (`list_resource.go`, for `terraform query`, Terraform 1.14+): a list resource has its managed resource's type name and is a constructor of the generic `listResource[C, T]` (`list_resource_product.go` is the template; `nameListResource` for those whose only filter is `name_contains`). Its fields: the schema; `all`, the client's lazy `ListAll` with DefectDojo's filters; `keep`, the filters checked on the client side; `results`, which builds each result (`modelResults` for a plain `update…Model`). **The state must be what an import followed by `Read` stores** (tag references null, `force_destroy` false), so that the generated configuration plans no changes: `TestListResourceStates` compares them for every registered list resource, which needs a row and a fixture there. `listResults` streams in DefectDojo's order and skips repeated IDs; a collection without a total order (webhooks, product attributes) is read whole and sorted (`sortedByID`), and an error result ends the stream. The singletons (`defectdojo_system_settings`, `defectdojo_announcement`) have no list resource. Filters: `name_contains` (ignoring case) uses DefectDojo's filter only where it already matches that way, else `containsFold`; scope filters (`product_id`, ...) are DefectDojo's, and a 400 for an unknown object becomes "not found". Every resource's acceptance test has an `ImportBlockWithID` + `GenerateConfig` step. Examples are `examples/list-resources/<type>/list-resource.tfquery.hcl`, rendered to `docs/list-resources/`.
- **Migration from `doximity/defectdojo`** (`move_state.go`): doximity's `defectdojo_product_type` and `defectdojo_product` have the same type names, so Terraform reads their states (schema version 0, the ID as a string, attributes of other names or types) with this provider once the provider source changes; a `moved` block to the same address is rejected as redundant. `TestUpgradeDoximityState` pins this: **a schema version bump of these two resources needs a state upgrader from version 0 that accepts doximity's states as well as ours.** `defectdojo_jira_project` has `MoveState` from `defectdojo_jira_product_configuration` (`moveFromDoximity`), which takes only the ID; the refresh in the same plan reads the rest. The acceptance tests (`move_state_acc_test.go`) run doximity 0.0.13 in their first step (`ExternalProviders`, `DEFECTDOJO_BASEURL`) on the guide's configurations in `examples/guides/migrating-from-doximity/`.
- Data sources look up by `id` or exact `name` (`datasourcevalidator.ExactlyOneOf`), using the client's `GetByName`, which re-checks the name on the client side. A data source's model can be filled from the resource's `update…Model` (`data_source_product.go`).
- Plural data sources (`data_source_test_types.go` is the template) take optional exact filters, re-checked on the client side, and return a computed list of objects sorted by name plus a `names` list; a filter that matches nothing gives empty lists, not an error.

## Test Patterns

Acceptance tests require a real DefectDojo. Tests follow this structure:
- `TestAcc<Resource>(t)`: create with defaults, update every attribute, import by ID, import by identity (`ImportBlockWithResourceIdentity`), changed outside Terraform (reverted), deleted outside Terraform (re-created). Plus tests for guards such as `force_destroy`.
- Configs omit the `provider` block: the provider reads the environment.
- `testAccClient(t)` returns a go-defectdojo client configured from the environment, to change or check objects in `PreConfig` and check functions. Objects the client cannot create yet are created with `client.NewRequest`/`Do`: `testAccCreateTest` creates a test in an engagement (with extra fields, such as `environment`) and returns its ID, `testAccCreateTestOutside` creates one with a product type, product and engagement of its own, and `testAccCreateNote` adds a note of a note type to a test; `testAccCreateSLAConfiguration` creates an SLA configuration with the default days that is deleted when the test ends; `testAccCreateProductType` creates a product type that is deleted, with its products, when the test ends.
- **The SLA lock** (go-defectdojo's "The SLA lock" quirk): a change of an SLA configuration's days or `enforce_*` attributes locks them and the SLA configuration of its products, and moving a product to another SLA configuration locks the product and the new configuration, until Celery recalculates the SLA dates; the test stack has no Celery worker, so the lock stays. Change days only on configurations the test created and at most once each, move a product at most once, to a configuration the test created, and never change the Default's days. `slaRecalculationHint` explains the 400 (`defectdojo.IsSLARecalculating`).
- Assertions use `statecheck.ExpectKnownValue` with `knownvalue`, `statecheck.CompareValuePairs`, `statecheck.ExpectIdentityValueMatchesState` and `plancheck.ExpectResourceAction`.
- Destroy after a test uses the last step's config, so end with a valid config after `ExpectError` steps.
- A regression test must fail without its fix: when two resources change in the same step, Terraform applies them in parallel, which can mask a bug. Change them in separate steps.

## Compatibility

From v1.0.0 the schema follows semantic versioning: a change that can break a configuration or a state written by the latest release needs a new major version. Two checks enforce it:
- `TestSchemaCompatibility` (`schema_compatibility_test.go`, in `make test`) compares the provider's schemas with `internal/provider/testdata/schema-baseline.json`, the schemas of the latest release: the protocol schemas of the provider, resources, data sources and list resources, the identity schemas, and each resource attribute's default and `RequiresReplace`. Removing or retyping anything, a new required attribute, an attribute that can no longer be set, Optional or Computed removed, Computed added to an Optional attribute (null no longer clears it), Sensitive or WriteOnly added, WriteOnly removed (only write-only attributes take ephemeral values), a changed or added default, a new `RequiresReplace`, a changed identity schema and a lower schema version fail; additions, deprecations, Required→Optional and removing `RequiresReplace` pass. Force replacement only with the framework's `RequiresReplace`, `RequiresReplaceIf` or `RequiresReplaceIfConfigured` attribute plan modifiers, never with `resp.RequiresReplace` in `ModifyPlan` or a modifier of our own, which the check can't see; resource attributes can't be nested (the dump stops). Only the release pull request changes the baseline, and it must regenerate it (`go test ./internal/provider -run TestSchemaCompatibility -update`) without changing the provider's code; a step of `build.yml` checks this.
- `TestAccUpgradeFromLatestRelease` (`upgrade_acc_test.go`) applies a configuration of the most involved resources with the latest release from the Registry (`upgradeFrom`), then expects an empty plan and the identities with this build. It runs with an empty `TF_CLI_CONFIG_FILE`, so `dev_overrides` can't replace the release, and is skipped on DefectDojo versions the release wasn't tested on (`upgradeFromDefectDojo`, a second list of DefectDojo versions besides `.github/defectdojo-versions.json`, frozen per release). The first pull request after a release raises both; the release pull request can't, as it runs before its tag exists.

## The client dependency

`go.mod` requires go-defectdojo by a pseudo-version of a commit on its `main` branch while a feature is in development (`GOPROXY=direct go get github.com/ottramst/go-defectdojo@<sha>`), never a commit of a pull request branch, which squash merges discard. Never commit a `replace` directive; `go.work` (gitignored) is for local development. `release.yml` fails when go-defectdojo is a pseudo-version: tag the client first.

## CI

GitHub Actions workflows in `.github/workflows/` (`main.yml` orchestrates `generate`, `lint`, `build`, `test`, and a single `CI gate` job used as the required status check):
- Acceptance tests run a matrix of DefectDojo (from `.github/defectdojo-versions.json`; a `versions` job also checks that every DefectDojo image in `docker-compose.yml` is tagged `${DD_VERSION:-<newest>}`) × Terraform {1.16.\*, 1.17.\*} (the two non-EOL minors)
- `upstream.yml` (scheduled, not in the CI gate): a nightly canary on DefectDojo's `nightly-dev` image, and a weekly job that opens an issue when a new DefectDojo minor is released
- All `setup-go` steps use `go-version-file: go.mod`, so `go.mod`'s `toolchain` line is the Go that CI and the released binaries use (govulncheck checks it too, with `go-version-input: ''`): raise it with each Go security release. All actions are pinned to commit SHAs
- `make generate` must produce no git diff, and `go.mod`/`go.sum` must be tidy
- golangci-lint enforced with zero tolerance (`max-issues-per-linter: 0`)
- Also: CodeQL, govulncheck and dependency review (`security.yml`), OpenSSF Scorecard, and actionlint plus zizmor for workflow changes. Reusable workflows are called with `./` paths plus `# zizmor: ignore[self-repository]`, because the `$/` syntax zizmor suggests fails actionlint
- `release.yml`: on a `v*` tag, in the `release` environment, GoReleaser builds and GPG-signs the artifacts (secrets `GPG_PRIVATE_KEY` and `PASSPHRASE`) and attests their provenance

## Rules

- Add a `CHANGELOG.md` entry under `## Unreleased` for user-visible changes (HashiCorp style: `BREAKING CHANGES`, `FEATURES`, `ENHANCEMENTS`, `BUG FIXES`, `NOTES`), linking the issue.
- Every resource needs examples (`resource.tf`, `import.sh`, `import-by-identity.tf`, `data-source.tf` for its data source, and `list-resource.tfquery.hcl` for its list resource), regenerated docs (`make generate`), and acceptance tests that pass on every supported DefectDojo version. Guides are `templates/guides/<name>.md.tmpl`, which tfplugindocs renders to `docs/guides/`, with their configurations in `examples/guides/<name>/` (included with `tffile`); every other page uses tfplugindocs' default template.
- Pull request titles follow Conventional Commits (`feat: add defectdojo_product`). PRs are squash-merged and reference their issue (`Closes #N`).
- Plans for a milestone, or for any change that spans several pull requests, go through the `plan-critic` subagent (`.claude/agents/plan-critic.md`) before they are approved. Spawn it with the plan file path and the decisions the user has made only, fold the confirmed findings into the plan, and note in the plan which were taken. Run it again if the findings change the plan's structure, such as its pull requests or their order.
- Every pull request, including Dependabot and release pull requests, gets an independent review by the `pr-reviewer` subagent (`.claude/agents/pr-reviewer.md`) before it is merged. Spawn it with the PR number and the PR's purpose only, not your own conclusions, so the review is independent. Fix confirmed findings on the PR branch, and have the fix commits reviewed again before merging.
